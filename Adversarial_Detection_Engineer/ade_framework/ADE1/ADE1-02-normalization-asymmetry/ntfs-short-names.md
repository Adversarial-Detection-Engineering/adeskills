# NTFS 8.3 Short Names

## Summary

NTFS generates DOS-compatible 8.3 short names for files and directories whose names exceed the 8.3 format. `C:\Program Files` becomes `C:\PROGRA~1`. When a process is launched using the short name path, some Sysmon versions log the short name in the Image field, bypassing rules that match on the long path.

## ADE Classification

**Category:** ADE1 — Reformatting in Actions
**Subcategory:** ADE1-01 — Substring Manipulation
**Core principle:** Two different strings (`C:\Program Files\...` and `C:\PROGRA~1\...`) resolve to the same filesystem location. Rules matching one path miss the other.

## The Technique

8.3 short names are auto-generated by NTFS when:
- The base filename exceeds 8 characters, OR
- The extension exceeds 3 characters, OR
- The name contains characters not allowed in DOS

Common mappings:
| Long Name | 8.3 Short Name |
|-----------|---------------|
| `C:\Program Files` | `C:\PROGRA~1` |
| `C:\Program Files (x86)` | `C:\PROGRA~2` |
| `C:\Windows\System32` | `C:\Windows\System32` (already 8.3 compliant) |

Files with names that already fit in 8.3 format (like `whoami.exe`, `cmd.exe`, `net.exe`) do NOT get auto-generated short names — they ARE the short name.

### Checking 8.3 status

```cmd
fsutil 8dot3name query C:
dir /x C:\
```

### Where this matters most

The technique is most impactful for paths through `Program Files` directories, where many security tools and applications live:

```cmd
C:\PROGRA~1\Mozilla Firefox\firefox.exe
C:\PROGRA~2\Microsoft\Edge\Application\msedge.exe
```

Rules matching `Image|contains: 'Program Files'` will miss `PROGRA~1`.

## Bypass Demonstration

### Benign test payload

```cmd
REM Check what short names exist
dir /x C:\

REM Execute via short name path
C:\PROGRA~1\PowerShell\7\pwsh.exe -c "whoami"
```

## Vulnerable Rule

```yaml
title: Suspicious Execution from Program Files
status: experimental
logsource:
    category: process_creation
    product: windows
detection:
    selection:
        Image|contains: 'Program Files'
    condition: selection
```

### Why it misses

When launched via `C:\PROGRA~1\...`, the Image field contains the short name, not `Program Files`.

## Hardened Rule

```yaml
title: Suspicious Execution from Program Files (Hardened)
status: experimental
logsource:
    category: process_creation
    product: windows
detection:
    selection:
        Image|re|i: '(Program Files|PROGRA~[12])'
    condition: selection
```

### Why the hardened rule works

The regex matches both the long name and the auto-generated short name variants.

## Sysmon Evidence

Behavior varies by Sysmon version. On the tested system (Windows 10, Sysmon 15.x):

| Launch Method | Image Field Shows |
|---------------|------------------|
| `C:\PROGRA~1\PowerShell\7\pwsh.exe` | May show short or resolved long name depending on Sysmon version |
| `C:\Program Files\PowerShell\7\pwsh.exe` | Long name |

The OriginalFileName field is NOT affected — it always comes from the PE header regardless of how the binary was launched.

## Detection Layers

| Layer | Detects? | Why |
|-------|----------|-----|
| Image path contains "Program Files" | No | 8.3 short name used instead |
| Image regex matching both forms | Yes | Covers PROGRA~1 and long name |
| OriginalFileName | Yes | PE header, path-independent |
| Image|endswith for binary name | Yes | `\pwsh.exe` matches regardless of parent path |

## Implementation Nuances

- See [Implementation Nuances](../../../bug_patterns/logging_assumption_errors.md) #10: NTFS 8.3 short names in Image field — behavior varies by Sysmon version
- 8.3 name generation can be disabled per-volume: `fsutil 8dot3name set C: 1` — but existing short names persist
- Some environments disable 8.3 names for performance, making this technique inert
- Prefer `Image|endswith: '\binary.exe'` over full-path matching — it is immune to path-format variations
